# Аудит утечек и высоких метрик

Аудит проверяет конкретные ошибки реализации на реальных артефактах.
Он не доказывает отсутствие любой утечки. Семантическая доступность
анонимизированных признаков и перенос на будущий период ими не подтверждаются.

## Проверки на реальных артефактах

Команда: `.venv/bin/python scripts/audit_leakage.py`.
Результат: [`reports/leakage_audit.json`](../reports/leakage_audit.json).
Требуются полный подготовленный набор, сохранённые scratch-предсказания и установленный проект (sklearn используется для независимого пересчёта).

- Пересечение клиентских ID между train, valid, test: ноль.
- Подготовленные ID уникальны, все исходные метки присутствуют и совпадают с оригинальным `train_labels.csv`.
- Split повторно вычисляется без использования target.
- В исходной схеме и агрегатах нет явных колонок target, label, split, prediction и score.
- Строки агрегатов проверены на повторяющиеся профили, в том числе между split.
  Использован 64-битный screening hash: это не формальное доказательство уникальности исходных историй.
- Сохранённые scores покрывают test-клиентов, и их метки совпадают с исходным CSV.
- AUC повторно вычислена через sklearn по исходным меткам, а не по сохранённой колонке target.
- Просмотрен путь обучения: fit принимает только train/valid; test оценивается после выбора checkpoint.
- Словари/квантили, contrastive-предобучение и ridge-проекция по коду используют только train.
  Регрессионные тесты дополнительно проверяют train-only чтение и frozen-tokenizer inference.

## Почему значения могут быть высокими

Gini 0.917 соответствует ROC-AUC 0.9585; это не 91.7% accuracy.
В текущем полном наборе один `P_2__last` даёт test AUC около 0.9158.
Направление ранжирования и импутация для этого контроля выбраны по train.
Источник сам содержит сильный сигнал. Случайное прореживание внутри класса само по себе не создаёт высокий ROC-AUC.
Это объясняет правдоподобие высокого качества,
но не позволяет установить бизнес-смысл и доступность каждого анонимного признака.

Мы проверяем уже существующих клиентов по истории выписок в одной когорте,
а не новый кредитный портфель и не новый временной период. Для применения в другом банковском скоринге нужна отдельная проверка качества.

## Уточнение формулы AmEx M

При независимой проверке заменена формула взвешенного Gini внутри AmEx M на точную
Lorenz-нормировку из референса соревнования. Прежняя эквивалентность через ROC-AUC
давала небольшую конечновыборочную погрешность: около 0.00000057 по M для полного
scratch-прогона. На высокий ROC-AUC и Gini 0.91703 эта поправка не влияет.
Итоговые AmEx-метрики пересчитываются из сохранённых предсказаний; тест сравнения
с независимым референсом ужесточён до 1e-12.

## Отрицательный контроль с перемешанными метками

Команда для существующей quick-ветки:

```bash
.venv/bin/python scripts/audit_label_shuffle.py
```

Либо фиксированная 3% подвыборка полного подготовленного набора:

```bash
.venv/bin/python scripts/audit_label_shuffle.py --source full
```

Новый supervised Transformer обучается с нуля на реальных историях. Метки независимо
перемешиваются внутри train, valid и test, а не между выписками одного клиента.
Контроль выполняется для seed 7, 42, 101, по две эпохи; численные результаты —
[`reports/label_shuffle_control.json`](../reports/label_shuffle_control.json).
Ожидаемый test AUC около 0.5. Это проверяет маршрут обучения/оценки и помогает обнаружить
случайное использование ответов или неверную оценку. При полном формировании отчёта
обе диагностические команды запускаются автоматически отдельными процессами.

Ограничение контроля: если исходный признак содержит информацию о будущем исходе,
после перемешивания target его связь с новой случайной меткой всё равно исчезнет.
Поэтому успешный shuffle-control не исключает семантическую утечку в исходном датасете.

## Открытые ограничения

1. Нет оригинального CSV: точность и происхождение стороннего parquet не подтверждены
   сравнением каждого значения. Проверены полнота и структура.
2. Анонимизация ограничивает проверку момента доступности каждого признака.
3. Нет размеченного локального OOT: клиентский holdout не заменяет временной.
4. Test уже просматривался в прежних исследованиях. Выбор новых гипотез по его
   результатам может привести к переобучению исследователя на test.
5. Один seed основного сравнения; bootstrap по клиентам не измеряет неопределённость обучения.

Корректная формулировка результата: «в проверенных сценариях явных ошибок реализации
и пересечений клиентов не обнаружено; качество измерено на локальном клиентском holdout AmEx».
Формулировки «утечек точно нет» и «банковский Gini будет таким же» не обоснованы.
